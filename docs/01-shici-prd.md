## 摘要

拾词目前已经形成“词书选择—今日概览—7 词微循环—客观提取—智能复习—词库管理—报告反馈”的完整学习闭环，并以 6 本词书、10,799 个词条覆盖高考、高中文言、大学四六级和雅思学习场景。现有产品具备明确的学习链路、分层评分、复习报告、双语语音、PWA 离线能力和 `localStorage + IndexedDB + serve.py /api/state` 三层防丢存储，已经具备可持续演进的产品骨架。

下一阶段的主要矛盾不在功能数量，而在三项信任基础：

1. **学习进度必须可信**：存储层存在，但多层之间的一致性、恢复顺序、迁移和冲突规则必须明确，确保任何单层故障都不造成进度丢失。
2. **学习内容必须可信**：10,799 个词条需要在统一内容契约下完成结构审计，尤其需要建立 `fallback-example` 的全量发现、人工复核、修正和回归闭环。
3. **学习反馈必须可解释**：自评、4 类客观提取、智能复习和报告需要保持计分口径分离，并让文言多义辨析从“看到解释”升级为“能够区分和迁移”。

演进顺序建议为：WorkBuddy × 本机 Codex CLI 与 `ego-browser` 协同贯穿各阶段；P0 先明确存储与内容契约、守住学习记录和内容发布底线，P1 增强学习体验与文言辨析，P2 在既有 JSON 导出/导入基础上探索增量合并及可选云同步。

## 一、产品愿景与演进目标

### 1.1 产品定位

拾词是一款面向高中生与大学生的中英文词汇与高中文言实词学习 Web App。产品以手机端高频、短时、可持续的学习为核心，通过词书、微循环学习、客观提取、智能复习、词库、报告和离线能力，帮助用户在考试备考与长期能力积累之间建立稳定学习节奏。

产品工作用愿景是：

> 让用户每天用较低负担完成可验证的词汇学习，记得住、辨得清、看得见进步，并且不会因为换设备、断网或存储异常而丢失学习成果。

该愿景是本文用于指导需求取舍的工作表述，不代表已确认的官方品牌口号。

### 1.2 核心学习链路

当前已核实的能力可以归纳为以下闭环：

```text
选择词书
  → 查看今日概览
  → 进入 7 词微循环
  → 卡片自评
  → 4 类客观提取并独立计分
  → 进入智能复习、复习已学或错词重学
  → 在词库中检索与管理
  → 在报告中查看保持率、自评分布、错误分类和热力图
```

产品演进应围绕这个闭环强化可信度、解释性和连续性，不以引入无关功能数量作为主要目标。

### 1.4 词书矩阵

当前共有 6 本词书，按各书词条数相加为 10,799 个“词书内词条”；`curated` 的核心 120 与 `wenyan` 总书共享词条身份和学习进度，因此 10,799 不是跨书去重后的唯一学习对象数。内容覆盖率按书统计，学习/报告指标须说明跨书去重口径。

| 词书标识 | 词书 | 词条数 | 当前结构 | 进度与审计重点 |
|---|---|---:|---|---|
| `gaokao` | 高中 3500 | 3,663 | 8 个乱序组 | 校验乱序组覆盖、重复词、组间词条归属 |
| `curated` | 文言精讲 120 | 120 | 6 个主题 | 与文言总书共享进度；需建立稳定词条映射 |
| `wenyan` | 高中文言重点字词 1200 | 1,200 | 核心 120 + 拓展 80 + 高频 1000，共 33 单元 | 校验三层构成之和、33 单元归属和共享进度一致性 |
| `ielts` | 雅思必背 | 3,426 | 当前数据未提供分组信息 | 大词书性能、分页、搜索与复习负载 |
| `cet4` | 四级核心 | 1,162 | 当前数据未提供分组信息 | 大学英语学习路径与错词复习 |
| `cet6` | 六级核心 | 1,228 | 当前数据未提供分组信息 | 四级到六级的进阶与重复词识别 |
| **合计** | **6 本词书** | **10,799** | — | 所有计数必须由同一内容清单可重复计算 |

其中，文言矩阵存在两个必须明确的产品约束：

1. `curated / 文言精讲 120` 与 `wenyan / 高中文言重点字词 1200` 总书共享进度。无论用户从精讲还是总书进入同一学习对象，其相关学习状态必须一致。
2. `wenyan` 的构成是核心 120、拓展 80、高频 1000，三者之和为 1,200；33 个单元必须覆盖全部词条，不能出现未归属、重复归属或单元外孤立词条。

### 1.5 当前产品优势

- 词书覆盖场景明确，从高考英语、高中文言延伸到四六级和雅思，能够支撑高中至大学的连续学习。
- 学习链路完整，不只提供浏览，还包含自评、客观提取、智能复习和错词重学。
- 自评与客观提取分离计分，具备比单一“会/不会”反馈更有解释力的基础。
- 报告覆盖保持率、自评分布、拼写错误分类和热力图，已有把学习行为转化为反馈的产品结构。
- 美音男女声、PWA 离线安装和本地常驻服务提高了日常使用的可触达性。
- 三层存储与 Schema v3 表明产品已有关注数据耐久和版本迁移的设计意识。

### 1.6 当前主要风险与演进机会

| 风险或机会 | 当前判断 | 演进方向 |
|---|---|---|
| 内容规模大 | 10,799 个词条已经超过仅靠人工抽查可稳定管理的规模 | 建立统一内容契约、自动结构审计、fallback 全量复核和发布门禁 |
| 多层存储不一致 | 当前 `localStorage` 同步写入，IndexedDB 异步副本失败可能静默；恢复多依赖时间戳和已学数 | P0 明确确认语义、主从迁移风险、恢复冲突规则和回归测试 |
| 线上与本机能力差异 | GitHub Pages 纯静态版本没有 `/api/state`；仅本机 `serve.py` 提供快照 | 保持线上浏览器保存、离线学习和手动导出/导入，清晰说明两种 origin 记录独立 |
| 文言共享进度 | 精讲 120 与总书共享进度，跨书映射必须稳定 | 使用稳定词条身份和显式映射，禁止依赖标题或数组下标 |
| 文言辨析深度 | 现有数据强调了文言词书和复习，但未说明是否已支持完整多义辨析 | P1 增强语境义项、古今异义、词类活用和易混对比 |
| 反馈可行动性 | 当前报告已包含保持率、自评分布和拼写错误分类 | 让每项报告结果可跳转到对应错词、复习任务或辨析练习 |
| 跨端连续性 | 设置页已有 JSON 导出/导入用于两种 origin 或设备间手动迁移；尚无账户或云同步，导入以整包写入为主 | P2 增加导入预览、幂等增量合并和回滚，再评估账号和云同步 |
| 产品指标基线 | 当前给定数据未包含活跃、完成率、留存或恢复成功率 | 先冻结事件口径和现状基线，再设定增长目标 |

### 1.7 演进目标

#### 目标 A：可信的数据基础

在继续扩展学习玩法和内容之前，确保词条身份、学习事件、派生状态、存储快照和版本迁移均有明确契约。至少一个确认成功的耐久存储层可用时，刷新、离线切换或单层故障不得丢失已确认结果；全部写入失败时不得显示“已保存”，应提示重试与可用的备份/恢复方式。浏览器站点数据被整体清除且无外部备份的情况不承诺零丢失。

#### 目标 B：可信的学习内容

以 10,799 个词条为完整审计母体，确保词书数量、分组数量、词条归属和共享进度关系可重复验证。所有 `fallback-example` 都必须被识别、复核、记录结论并纳入回归检查，不能以默认兜底文案长期替代高质量例句。

#### 目标 C：可解释、可迁移的学习效果

保留 7 词微循环带来的低负担节奏，同时让用户理解“自评掌握”“客观提取正确”与“复习安排”之间的关系。文言学习要从单点释义扩展到同一字词在不同语境下的辨析和迁移。

#### 目标 D：持续的跨端学习

保留现有用户可控的 JSON 导出、导入，增加合并前预览、幂等去重和可回滚操作，再评估账号化与云同步。跨端增强不得导致另一端独立学习记录被整包覆盖。

#### 目标 E：可审计的协同交付

将 PRD、内容审计报告、状态契约、测试结果和待确认事项转化为 WorkBuddy 与 Codex 可共同读取的结构化交付物，形成“需求—实现—验证—人工复核”的闭环。

## 二、核心用户画像与用户故事（User Stories）

### 2.1 核心用户画像

| 画像 | 典型场景 | 核心任务 | 主要痛点假设 | 成功体验 |

| 高三英语冲刺生 | 每天利用 10–15 分钟学习高中 3500，优先处理错词和到期复习 | 完成 7 词微循环、客观提取、错词重学，查看 24h/7d 保持率 | 自评可能高估掌握程度；碎片时间下不愿操作复杂；中断后担心进度丢失 | 每天能快速继续任务，客观得分和复习结果能明确指出下一步 |

| 断续使用者 | 期中、考试周或假期中断后重新开始 | 恢复上次进度、清理到期复习、重学错词 | 中断后不知道从哪继续；报告看得懂但不知道点哪里行动 | 首页直接给出继续学习入口，报告项可跳转到对应任务 |

以上“主要痛点”属于基于现有功能结构提出的产品假设，需通过访谈或行为数据进一步验证。

### 2.3 用户故事清单

### 3.2 P0：架构解耦与状态零丢失

#### 3.2.1 目标

将当前已经存在的功能能力从页面和单一状态实现中解耦，形成稳定的内容、学习领域、复习引擎、持久化和展示边界。确保 `shici.state.v1` 与 Schema v3 的升级、写入、恢复和快照过程具备可验证的数据不变量。

#### 3.2.2 目标逻辑架构

建议按以下逻辑模块建立边界，可沿用现有技术栈实现，不强制引入新框架：

| 模块 | 职责 | 不得承担 |
|---|---|---|
| 内容目录层 | 词书清单、词条身份、分组、主题、单元、共享进度映射、内容版本 | 不直接保存用户会话状态 |
| 学习领域层 | 7 词会话、自评、4 类客观提取、错词、复习和派生掌握状态 | 不依赖具体 DOM 节点 |

| 持久化层 | Schema 校验、事务写入、快照、迁移、恢复、冲突检测 | 不静默吞掉失败 |

| 平台层 | 本机服务、PWA 缓存、在线/离线能力探测、安装状态 | 不把服务可用性等同于数据已保存 |

#### 3.2.3 状态领域模型

目标状态模型至少需要能够区分以下实体或等价信息：

| 实体 | 关键内容 | 数据原则 |
|---|---|---|
| 内容版本 | 词书、词条、分组、主题、单元、映射版本 | 内容更新可追踪，历史学习可解释 |
| 学习会话 | 词书、模式、开始时间、词条顺序、当前步骤、完成状态 | 支持中断恢复，避免半状态 |
| 词条尝试 | 自评值、4 类客观提取结果、错误分类、时间、会话引用 | 作为增量事件保存，不能只覆盖最终结果 |
| 派生词条状态 | 已学、错词、待复习、掌握等状态及计算依据 | 可从历史事件重建，不成为唯一事实来源 |
| 复习计划 | 到期时间、推荐原因、来源错误或保持率信号 | 算法升级后仍能解释旧任务 |
| 用户设置 | 声音选择、筛选偏好、必要的界面设置 | 与学习历史分离 |
| 快照元数据 | Schema 版本、应用版本、内容版本、修订号、生成时间、摘要校验 | 用于选择恢复来源和检测损坏 |

当前 `js/store.js` 已定义 Schema v3 的 `profile`、`words`、`activity`、`bookSeeds`、`meta` 及词条记录字段。本 PRD 不重复逐项抄写源码；实施前应从源码提取字段契约、迁移清单与历史兼容测试，再讨论事件化扩展。

#### 3.2.4 建议的耐久写入顺序

现状为 `localStorage` 同步保存主状态、IndexedDB 异步写入恢复副本、本机 `/api/state` 异步快照；IndexedDB 失败路径可能静默。目标不是“写过三次”，而是在至少一个耐久层确认成功后才显示保存成功，全部失败必须明示。下述 IndexedDB 主存储方案是待验证设计，需先验证 Safari、配额、离线与旧状态迁移，不能直接当作现状。

建议语义如下：

1. 学习操作在内存事务中生成不可变事件和新的派生状态。
2. 使用 Schema 校验内容、必填字段、枚举和引用关系。
3. 先将增量事件和状态变更事务性提交到 IndexedDB，作为本地耐久层。
4. 提交成功后更新 `localStorage` 的紧凑热缓存或恢复摘要。
5. 仅在本机服务可用时，异步写入 `serve.py /api/state` 快照。
6. 页面只有在本地耐久提交成功后，才向用户显示“已完成/已保存”。
7. API 快照失败只记录为降级状态，不回滚已经成功保存的本地学习结果。

现有代码已核实先同步写 `localStorage`，再异步发起 IndexedDB 写入；以上顺序仅为演进提案，实际切换必须以兼容性和迁移测试为前提。

#### 3.2.5 恢复和冲突原则

- 快照必须携带 Schema 版本、修订号、内容版本和完整性校验，不得只比较更新时间字符串。
- 同一学习事件必须有稳定事件标识，重试写入应幂等。
- 学习尝试原则上采用增量合并，不能因恢复旧快照而删除新事件。
- 派生状态由事件和版本化规则重算；无法重算时保留最后一次可验证快照并明确标记。
- 内容中已经不存在的旧词条不能直接删除，应进入归档状态，避免历史报告失真。
- 用户设置等单值状态需定义明确冲突规则；无法自动裁决时向用户展示差异并要求确认。
- Schema 升级必须先备份，再迁移；迁移失败应保留旧版本，不得只留下半迁移状态。

#### 3.2.7 状态零丢失测试矩阵

| 故障场景 | 预期行为 | 禁止行为 |
|---|---|---|
| 完成一次客观提取后立即刷新 | 结果保留，会话位置可恢复 | 回到未作答状态 |
| 页面关闭发生在写 API 快照之前 | 本地结果有效，API 状态为待补写或可忽略 | 整次学习被判定失败 |
| IndexedDB 可用、`localStorage` 写入失败 | 从 IndexedDB 正常恢复 | 页面显示已保存但重开后丢失 |
| `localStorage` 可用、IndexedDB 暂时不可用 | 展示明确降级提示，并保护已有状态 | 静默覆盖旧数据 |
| 本机 4173 服务不可用 | 线上或离线模式继续，显示增强能力不可用 | 阻断全部学习 |
| API 返回旧快照 | 根据事件和修订检测，不覆盖本地新事件 | 仅按“最新更新时间”整包覆盖 |
| 相同备份或事件重复写入 | 幂等去重，统计不翻倍 | 重复增加错误次数或复习次数 |
| 迁移中途失败 | 保留原 Schema 状态并可重试 | 留下部分新字段、部分旧字段的不可识别状态 |
| 内容升级后旧词条消失 | 历史可解释，旧尝试归档 | 报告数字突然无因下降 |
| 浏览器清除单一缓存层 | 仍可从另外的耐久层恢复 | 要求用户重新学习已完成内容 |

#### 3.2.8 部署一致性要求

线上地址使用 GitHub Pages 静态托管，而 `/api/state` 快照由本机 `serve.py` 提供。由此必须明确：

- GitHub Pages 纯静态站没有本机 `/api/state`；线上与 `127.0.0.1:4173` 是不同 origin，浏览器状态互不自动共享。
- 线上明确显示浏览器存储模式，保持现有手动 JSON 导出/导入能力，不能把预期的 API 缺失显示为学习失败。
- 所有 P0 学习与恢复能力至少应在没有 `/api/state` 的情况下成立。
- 本机 4173 服务可作为增强恢复层，但不得成为唯一可用路径。
- 同一份状态 Schema 在线上、离线 PWA 和本机服务中必须一致；无法支持的能力通过能力标志隐藏或降级。

### 3.3 P0：内容审计与 fallback-example 复核闭环

#### 3.3.1 审计范围

内容审计以当前 6 本词书、10,799 个词条为完整母体，不以抽样替代总量核对。

必须验证：

1. 各词书实际词条数与声明数一致。
2. 6 本词书之和等于 10,799。
3. `gaokao` 的 8 个乱序组完整覆盖 3,663 个词条，组间重复符合明确策略。
4. `wenyan` 的核心 120、拓展 80、高频 1000 之和为 1,200，33 个单元完整覆盖。
5. `curated` 的 6 个主题完整覆盖 120 个词条。
6. `curated` 与 `wenyan` 总书的共享进度映射完整、唯一且可解释。
7. 每本词书内和跨词书的重复词条策略明确，避免错误合并不同义项。
8. 所有词条的例句、翻译、词义、辨析字段引用有效。
9. 所有 `fallback-example` 均被识别，不被统计为普通自主例句。

#### 3.3.2 fallback-example 的工作定义

现有构建脚本为缺少例句的英文词条生成可追踪课堂例句，并写入 `contentFlags: ["fallback-example"]`；`tools/export_content_review.py` 已导出人工复核队列，审核前不自动覆盖词书。当前共有 **508 个唯一词**待审核，其中 P0 99、P1 220、P2 189；各词书计数因跨书重复不能相加作为唯一词数。后续需补齐审核状态、来源和回归证据，不得把自动生成句误标为已人工校订。

#### 3.3.3 内容质量问题分级

| 等级 | 定义 | 示例 | 发布要求 |
|---|---|---|---|
| C0 阻断 | 会造成错误学习、答案错误或进度错乱 | 义项与例句完全不符、客观答案错误、共享进度映射到错误词 | 必须修复后才可发布 |
| C1 严重 | 明显误导、来源或翻译不可靠、重要辨析缺失 | 古今义混淆、翻译改变句意、fallback 无法体现目标义项 | 必须修复或完成有依据的豁免 |
| C2 一般 | 可理解但表达、格式、难度或一致性有问题 | 标点不一致、例句过长、英文大小写不统一 | 进入计划修复 |
| C3 优化 | 不影响正确性的风格提升 | 更自然的表达、更贴近场景的例句 | 可随版本迭代 |

#### 3.3.4 复核闭环状态

建议使用以下状态或等价状态机：

```text
未复核
  → 待复核
  → 复核中
      → 通过
      → 需修正
          → 已修正，待复审
              → 通过
      → 有依据豁免
```

每个 fallback 至少要具备：

- 稳定词条身份和词书范围。
- fallback 类型与触发原因。
- 原例句或当前后备句。
- 目标词义、词性、读音和必要语境。
- 中文释义或翻译。
- 来源或生成依据。
- 审核人和审核时间。
- 结论、修正版本和回归时间。
- 是否为 C0/C1 阻断项。

#### 3.3.5 复核检查清单

- 例句是否真正覆盖当前词条的目标义项，而不是只包含拼写。
- 英文例句是否自然、语法正确、难度适合目标用户。
- 中文翻译是否与例句一一对应，不遗漏否定、时态或语气。
- 文言例句是否存在可靠出处，释义是否与具体语境一致。
- 同一文言字在多个义项之间是否有足够区分信息。
- 例句是否包含不必要的敏感、歧视、广告或外部品牌内容。
- 例句长度在 390px 卡片和移动端排版中是否可用。
- TTS 是否能合理朗读英语例句；文言和中文朗读能力不擅自假设。
- fallback 是否因长期未补主例句而造成学习质量下降。
- 修正后是否触发相关辨析、拼写错误分类和报告的回归检查。

#### 3.3.6 P0 内容审计需求清单

| 需求 ID | 需求 | 验收要点 |
|---|---|---|
| P0-AUDIT-01 | 建立不可变的词书与词条清单基线 | 6 本词书计数和总盘 10,799 可重复核对 |
| P0-AUDIT-02 | 建立统一内容字段契约 | 必填、可空、枚举、引用和版本规则明确 |
| P0-AUDIT-03 | 全量识别 fallback-example | 每个 fallback 可从报告定位到具体词条和词书 |

| P0-AUDIT-05 | 建立内容修正的版本和回归机制 | 修正可追溯，不以覆盖原文作为唯一记录 |

#### 3.3.7 内容验收底线

P0 内容阶段完成时，应同时满足：

- 10,799 个词条在清单中可被完整统计，无未解释缺失。
- 6 本词书的声明数和实际数一致。
- `wenyan` 的 120 + 80 + 1,000 与 33 单元均可核对。
- `curated` 与总书的共享进度映射有明确规则和验证结果。
- 对存量 508 个唯一待审核词形成分批复核计划，优先关闭高风险 P0 99 条；以全量结论记录作为内容质量里程碑验收，不把存量队列全清作为每个无关修复版本的前提。新增/修改的 fallback 在其内容发布前须完成审核。
- 不存在未解决的 C0 内容缺陷。
- C1 缺陷要么全部修复，要么具备书面豁免理由和影响说明。
- 每个已修复问题都能从原问题追踪到修正版本和回归结果。

### 3.4 P1：学习体验与文言辨析增强

#### 3.4.1 学习体验原则

1. 保留 7 词微循环的短会话节奏，不因功能扩展把每日学习变成复杂流程。
2. 自评与 4 类客观提取继续独立展示和独立计分。
3. 复习推荐应可解释，用户可以知道“为什么现在复习这个词”。
4. 报告中的每个主要异常都应能跳转到可执行任务。
5. 新功能优先服务“记住、辨清、再认、迁移”，而不是增加无目的点击。

#### 3.4.2 学习中心增强需求

| 需求 ID | 需求 | 验收要点 |
|---|---|---|
| P1-STUDY-01 | 在 7 词微循环中显示清晰阶段、当前词序号和完成进度 | 用户知道当前是第几个词、还有几个 |
| P1-STUDY-02 | 优化 P0 会话恢复后的续学提示 | 在 P0 已保证一致恢复基础上，清楚显示恢复位置、未提交步骤和继续操作 |
| P1-STUDY-03 | 自评结果与 4 类客观提取结果分区呈现 | 不生成掩盖两者的单一结果，口径标签固定 |
| P1-STUDY-04 | 增加学习结果解释 | 说明本题错误、相关义项、下一步复习或重学原因 |
| P1-STUDY-05 | 智能复习展示推荐依据 | 至少可区分到期、错词、低稳定性和近期失败等原因 |
| P1-STUDY-06 | “复习已学”明确范围和空状态 | 无到期或已学内容时给出可行动说明 |

| P1-STUDY-09 | 学习操作具备即时反馈 | 点击、选择、切卡和提交都有清晰状态，避免重复提交 |
| P1-STUDY-10 | 不因新交互破坏 PWA 离线学习 | 关键步骤在离线状态下可用或明确不可用原因 |

#### 3.4.3 词库与报告联动

| 需求 ID | 需求 | 验收要点 |
|---|---|---|
| P1-LIB-01 | 搜索词条时可同时组合 7 种状态筛选 | 结果计数与报告口径一致 |
| P1-LIB-02 | 分页保持稳定排序 | 翻页不重复、不遗漏，返回后保留合理上下文 |
| P1-LIB-03 | 报告项支持下钻 | 从自评分布、拼写错误分类和保持率进入相关词条或任务 |
| P1-LIB-04 | 热力图与报告时间范围联动 | 24h/7d 切换后标题、统计和空状态一致 |
| P1-LIB-05 | 拼写错误诊断提供可行动反馈 | 显示错误类型、相关词条和重练入口，而不只是图表 |

#### 3.4.4 文言辨析增强

文言学习需要从“词条释义”升级为“语境义项能力”。

建议的内容结构包括：

- 同一字词的多个稳定义项。
- 每个义项的语境条件、词性变化和使用方式。
- 古今异义与易误用说明。
- 形近字、同音字、同义或反义易混项。
- 带有可靠来源的例句和翻译。
- 目标义项与例句之间的明确对应关系。
- 由易到难的语境辨析练习。

建议新增以下需求：

| 需求 ID | 需求 | 验收要点 |
|---|---|---|
| P1-WENYAN-01 | 一个文言字词可保留多个稳定义项 | 不同义项不互相覆盖，共享进度仍以明确规则计算 |
| P1-WENYAN-02 | 词条展示语境义与通常释义的差异 | 用户能看出该句为什么采用该义项 |
| P1-WENYAN-03 | 增加古今异义和词类活用的辨析信息 | 内容经复核，不将通用说法误当具体出处 |
| P1-WENYAN-04 | 增加同类字词对比 | 可比较词义、用法、语境和典型错误 |
| P1-WENYAN-05 | 提供语境义项选择题或判断练习 | 题目必须由目标义项和有效例句驱动 |
| P1-WENYAN-06 | 错题反馈解释为什么其他义项不适用 | 不机械显示“错”，要给出语境依据 |
| P1-WENYAN-07 | 支持从文言精讲进入总书对应词条 | 共享进度不因跨书跳转而中断 |
| P1-WENYAN-08 | 文言词条的例句和义项具备审计状态 | 不使用未复核 fallback 作为关键辨析依据 |
| P1-WENYAN-09 | 文言学习状态与报告可解释 | 区分“看到过”“自评掌握”“客观辨析正确”等层级 |
| P1-WENYAN-10 | 保持 390px 下多义项内容可读 | 不依赖横向大表或悬停操作 |

#### 3.4.5 报告与诊断增强

报告应从“展示结果”转向“驱动下一步学习”：

- 24h/7d 保持率旁边展示对应到期复习入口。
- 自评分布明确区分主观评价和客观提取结果。
- 拼写错误分类显示问题词条、错误类型和重学按钮。
- 热力图支持查看近期学习范围，并说明空白日期代表未学习、无任务还是数据不可用。
- 统计数字必须可解释来源和计算时间范围。
- 不使用颜色作为唯一状态提示。

### 3.5 P2：跨端备份合并与 WorkBuddy × Codex 协同

#### 3.5.1 跨端备份与合并目标

现有设置页已有 JSON 导出、导入和本机快照恢复；GitHub Pages 仅有浏览器存储及手动文件迁移，未提供账号或云同步。P2 在现有整包导入/导出之上增加版本校验、导入预览、幂等增量合并与回滚，而不是从零建设备份，也不直接假定建设云端账户体系。

#### 3.5.2 备份文件要求

备份应包含：

- Schema 版本、应用版本和内容版本。
- 导出时间和安装实例标识。
- 学习会话与词条尝试事件。
- 派生状态或可重建派生状态的必要信息。
- 用户设置。
- 完整性摘要。
- 对旧内容词条的归档引用。

导入时必须先预览：

- 新增事件数。
- 已存在并跳过的事件数。
- 冲突数和冲突字段。
- 未知词书或未知词条数。
- 将被归档但不会删除的历史项。
- 合并后报告统计预计变化。

不得采用简单的“整个文件以最新时间覆盖旧文件”策略，因为这会丢失另一设备上的独立学习事件。

#### 3.5.3 合并规则建议

| 数据类别 | 合并建议 | 风险控制 |
|---|---|---|
| 学习尝试事件 | 按稳定事件 ID 求并集，重复事件幂等忽略 | 不得用最终状态覆盖历史事件 |
| 复习和错词派生状态 | 合并事件后按版本化规则重算 | 必须能解释与旧报告差异 |
| 用户设置 | 按明确优先级或用户选择合并 | 无法裁决时展示差异 |
| 已删除或下线内容 | 保留归档并排除未来任务 | 不无提示删除历史 |
| 报告聚合值 | 不直接合并数字，重新由事件计算 | 防止重复统计和口径混杂 |
| 内容版本差异 | 保留内容版本来源，标记未知词条 | 不把未知词条误映射到相似词 |

#### 3.5.5 WorkBuddy × Codex 协同定位

**本轮 P0 跨阶段交付机制**：WorkBuddy 的产品/架构/工程/QA 与本机 Codex CLI 共享需求 ID、实现计划和验证证据；Codex 负责可审阅的代码变更与 `ego-browser` 关键链路自动化，QA 独立复核 390px、离线、存储与内容门禁，主理人保留合并/发布决定。P2 仅指协同工具链扩展，不是把本轮协同延后。不得访问真实学习进度或将敏感数据写入普通协作日志。

该协同默认按“内部研发与内容运营”理解：

- WorkBuddy 负责产品需求、用户场景、验收意见和发布决策载体。

## 四、UI/UX 与 390px 响应式交互规范

### 4.1 设计目标

390px 移动视口是核心验收尺寸。界面应做到：

- 单手可完成主要学习操作。
- 不因中英文混排、长词、长例句或多义项产生页面横向滚动。
- 用户随时能判断当前任务、进度、保存状态和离线状态。
- 自评、客观提取、保持率和错误分类的口径不会被视觉混用。
- 重要信息不依赖颜色、悬停或长按才能理解。
- 新可访问性能力与 PWA、离线、三层存储状态保持一致。

### 4.2 视口和基础布局规范

以下为建议基线值，最终视觉稿可微调，但必须满足对应的验收要求：

| 项目 | 390px 规范 |
|---|---|

### 4.3 信息架构与路由导航

现有五个核心路由继续作为产品稳定入口：

| 路由 | 页面 | 主要职责 |
|---|---|---|
| `#home` | 今日概览 | 今日任务、继续学习、待复习、错词或近期进度的统一入口 |
| `#books` | 词书书架 | 6 本词书、词条数、结构标签、进度和入口 |
| `#study` | 学习中心 | 7 词微循环、自评、4 类客观提取、复习已学、错词重学 |
| `#library` | 我的词库 | 搜索、7 种状态筛选、分页和词条状态浏览 |
| `#report` | 学习报告 | 24h/7d 保持率、自评分布、拼写错误分类和热力图 |

建议底部导航顺序为：

```text
首页 | 词书 | 学习 | 词库 | 报告
```

该顺序属于本 PRD 的交互建议，不代表已核实当前导航顺序。

在 390px 下：

- 五个入口使用固定底部导航，不折叠进“更多”菜单。
- 当前路由具有文字、图标和可访问状态标识，不能只靠颜色。
- `#study` 进入活跃 7 词会话后，可切换为专注模式：保留退出、当前词序号和总进度；底部主导航是否隐藏必须在设计与实现中统一，退出活跃会话前应避免误触丢失。
- 每个路由应有浏览器历史可预测行为，返回键不能导致无提示的数据丢失。

### 4.4 通用视觉层级

建议采用四层信息结构：

1. 页面标题或当前任务。
2. 当前最重要的下一步动作。
3. 进度、得分或风险信息。
4. 解释、历史记录和次要操作。

原则：

- 一屏只设置一个视觉主按钮。
- 取消、重置和清空操作不得与主学习按钮同等突出。
- 自评掌握度、客观提取分数、保持率分别使用固定名称和固定颜色语义，不得混叫“得分”。
- 正误状态同时使用文字或图标，不只依靠红绿。
- 文言多义项、英文长句和错误解释使用可折叠内容时必须保留摘要，避免用户看不到关键信息。

### 4.5 390px 页面级规范

#### 4.5.1 `#home` 今日概览

建议首屏优先呈现：

1. 今日学习状态。
2. 继续当前学习或开始下一次 7 词微循环的主按钮。
3. 待复习数量及入口。
4. 错词数量或近期需要重学的提示。
5. 最近一次学习或报告摘要。

布局要求：

- 首屏主按钮必须在 390 × 844 视口内可见。
- 卡片纵向排列，不采用需要横向滑动才能发现关键任务的轮播。
- 存在未完成会话时显示“继续学习”，并显示当前进度。
- 无任务时展示可行动空状态，例如选择词书或查看复习，而不是空白。
- 离线时显示离线学习是否可用，以及最后一次本地保存时间。

#### 4.5.2 `#books` 词书书架

6 本词书建议采用单列卡片，避免在 358px 内容宽度内将中英文标题、词条数、分组信息、进度和操作相互挤压。

每张词书卡片至少展示：

- 词书名称和稳定标识对应的可读名称。
- 词条数。
- 结构摘要，例如 8 个乱序组、6 个主题、33 单元。
- 当前学习进度。
- 共享进度提示，仅用于 `curated` 与 `wenyan` 等真实共享场景。
- 进入词书或继续学习的主操作。

若使用两列卡片，必须验证：

- 中文标题、3,663、1,200 等数字不折行错位。
- 进度和按钮均有 44px 触控区域。
- 文本放大后不重叠。

默认建议使用单列。

#### 4.5.3 `#study` 学习中心

一个 7 词微循环的界面应保持：

- 当前词序号，例如“第 3/7 词”。
- 进度条或等价进度信息。
- 当前学习卡片。
- 自评操作区，或客观提取操作区；同一时刻明确当前任务。
- 英语 TTS 男女声入口，避免与提交按钮混淆。
- 当前保存状态只在必要时出现，不能让每次操作都被“保存中”打断。

交互要求：

- 自评和 4 类客观提取在视觉上分区。
- 结果页同时展示时，先展示作答结果，再展示解释或下一步。
- “下一词”“提交”“重学”“继续复习”等按钮每屏只突出一个主动作。
- 防止双击重复提交；重复点击不能产生重复事件。
- 中断恢复时显示“继续上次第 N 词”，不得无提示从第 1 词开始。
- 7 词完成后明确显示本次会话结果和下一次建议。

#### 4.5.4 `#library` 我的词库

390px 下建议：

- 搜索框固定位于页面标题下方或滚动时保持吸顶。
- 7 种状态筛选使用可横向滑动的 Chip 组，但页面本身不横向滚动。
- 当前筛选条件有明确选中态和可清除入口。
- 词条行至少包含词条、主要释义或状态摘要，以及进入详情或操作的入口。
- 状态徽标同时有文字，不只以颜色表示。
- 分页按钮位于列表末尾，显示当前页和是否还有下一页。
- 搜索无结果、筛选无结果和网络/离线不可用使用不同空状态。

组合筛选时应显示当前条件摘要，避免用户不知道自己为何看不到词条。

#### 4.5.5 `#report` 学习报告

首屏应优先显示时间范围切换和核心保持率。

- 24h/7d 切换控件使用分段控制或等价明确组件。
- 保持率同时展示时间范围和定义，避免误读。
- 自评分布使用带文本图例的图表或条形图。
- 拼写错误分类展示类别名称、数量或比例，并支持进入相关词条。
- 热力图在 358px 内按周组织；周数过多时仅允许图表容器横向滚动，页面不横向滚动。
- 每个趋势或异常区块应有“查看对应复习/错词”的操作。
- 数据为空、数据不足、离线缓存可用和统计失败必须有不同提示。

报告图表必须提供文本摘要，确保屏幕阅读器和色觉差异用户能够获得同一核心结论。

### 4.6 触控、手势与反馈

| 交互 | 规范 |
|---|---|
| 触控目标 | 不小于 44 × 44px；相邻目标之间至少保留 8px 间隔 |
| 主操作 | 位于拇指易达区域，滚动长页时可用安全区感知的底部固定操作条 |
| 反馈 | 点击后 100ms 内出现视觉反馈；提交后显示进行中状态 |
| 防止重复提交 | 提交中禁用重复触发，操作要有幂等保护 |
| 底部浮层 | 最大高度约为 `88dvh`，内容可滚动，关闭入口始终可达 |
| 搜索 | 建议在输入停止后再查询；以真实性能测试确认延迟，不造成输入卡顿 |
| 分页 | 翻页后滚动到列表起点，并保留筛选条件 |
| 返回 | 活跃学习会话、导入或删除等高风险动作必须提示 |
| 长按 | 不得作为核心学习操作的唯一入口 |
| 悬停 | 不得承载必要信息，所有信息触屏可达 |
| 自动播放 | 保留现有“切到下一张新词时自动朗读一次”，翻释义、收藏或返回不重复播放；如新增静音/关闭设置，应让用户可控，声音失败不阻断学习 |
| 动画 | 支持减少动态效果模式，持续动画可关闭 |

### 4.7 TTS 交互规范

当前已核实英语 TTS 为 `en-US` 男女声。

在 390px 下：

- 男女声入口必须标明声音差异，不能只用两个无标签扬声器图标。
- 当前声音选择应可见，并跨学习词条保持一致。
- 发音按钮最小触控区域为 44 × 44px。
- 同一时刻只允许一个主要朗读任务，避免重叠播放。
- 朗读中提供暂停、停止或重新播放中的必要状态。
- 浏览器不支持指定声音时明确显示降级说明，不显示“无响应”。
- 现有学习卡新词自动朗读一次：英文使用 `en-US` 当前偏好，中文词书使用中文语音；具体声线由浏览器/系统提供，文言准确读音和离线可用性须单独验证，不保证每个平台具备真实男女两条声线。
- 语音播放失败不得阻塞词汇学习的主流程。

### 4.8 离线与持久化状态呈现

界面应区分以下状态：

| 状态 | 用户可见信息 |
|---|---|
| 在线且所有增强能力可用 | 不额外打扰，只在设置或状态详情中显示 |
| 在线但 `/api/state` 不可用 | “本机增强快照不可用，学习仍会保存在本机” |
| PWA 离线且本地学习可用 | “当前离线，学习进度保存在本机” |
| 本地状态恢复中 | 展示恢复进度，避免用户开始重复学习 |
| 恢复自历史快照 | 告知恢复时间和影响范围 |
| 存储空间不足 | 明确阻止破坏性操作并提供导出/清理建议 |
| 恢复失败 | 提供重试、查看历史快照和导出入口 |
| 内容版本不匹配 | 说明哪些旧词条被归档或无法继续复习 |

存储失败不能使用模糊的“网络错误”掩盖。用户需要知道是网络、API、离线缓存还是浏览器存储问题。

### 4.9 响应式断点建议

| 宽度范围 | 布局建议 |
|---|---|
| 320–389px | 单列布局；缩小非关键间距；筛选 Chip 可横向滑动；图表保持可读 |
| 390–479px | 核心验收布局；16px 页面边距；主按钮高度至少 48px |
| 480–767px | 内容区可增加最大宽度并居中，避免卡片无限拉伸 |
| 768px 及以上 | 可扩展为内容容器居中布局；不要求立即增加桌面复杂分栏，但必须保持路由、键盘和可访问性可用 |

无论宽度如何，不应因桌面布局而破坏核心学习流程或隐藏报告关键信息。

### 4.10 可访问性规范

目标为符合现代移动 Web 可访问性要求，具体合规审计另行执行。

至少包含：

- 正文和控件满足 WCAG 2.2 AA 目标所需的对比度。
- 所有图标按钮具有可访问名称。
- 键盘焦点清晰可见。
- 表单、搜索框、筛选器和自评选项具有可读标签。
- 支持 200% 文本放大，不丢失关键操作。
- 图表提供表格、摘要或等价文本描述。
- 状态、正误和趋势不只依赖颜色。
- 触摸目标、错误提示和弹层关闭方式具备一致性。
- 遵循减少动态效果偏好。
- TTS 作为辅助能力，不作为唯一信息载体。

### 4.11 390px 关键验收场景

1. 在 390 × 844 视口打开 6 本词书，所有词书名、词条数和进度可见，无横向滚动。
2. `#home` 首屏能看到今日任务或继续学习主按钮。
3. 完成 7 词微循环时，任意时刻可辨认当前序号和阶段。
4. 自评与客观提取结果同屏时不混淆标签和分值。
5. 7 种筛选在 Chip 区可访问，横向滑动不导致页面整体移动。
6. 报告切换 24h/7d 后，标题、数据和空状态一致。
7. 热力图和图表不撑破主容器。
8. 底部导航、固定按钮和键盘输入区适配安全区。
9. 文本放大至 200% 后仍能完成核心学习流程。
10. 断网、恢复快照和 `/api/state` 不可用时，状态提示可理解且学习不被无故阻断。

## 五、验收标准与待确认事项

### 5.1 总体验收原则

- 现状计数必须使用同一内容清单和同一脚本或无歧义统计口径重复验证，并区分书内词条之和与跨书唯一词条。
- P0 验收以“至少一个耐久层确认成功后不丢已确认结果”为底线；全部层写入失败时不得显示已保存，测试范围须写明。
- 内容验收以 10,799 个书内词条的全量结构审计为底线；存量 508 个唯一 fallback 的全量结论作为内容质量里程碑，常规修复版本按变更范围执行门禁。
- 390px 验收必须覆盖真实移动交互，不以桌面浏览器缩窄窗口替代全部验证。
- 离线、恢复、导入和合并必须在低网络或单层故障场景下验证。
- 所有“未验证”“不可用”“降级”状态必须明确呈现，不能静默成功。
- 任何发布都应有明确的 P0 阻断项清单和关闭结论。

### 5.3 P0 架构与状态验收

| 验收 ID | 验收项 | 通过标准 |
|---|---|---|
| AC-P0-A01 | Schema 契约 | `shici.state.v1` 与 Schema v3 的字段、必填项、引用和迁移关系有文档 |

| AC-P0-A09 | 降级提示 | `/api/state` 不可用、离线或浏览器存储异常时提示明确，不伪装为网络错误 |
| AC-P0-A10 | 共享进度 | `curated` 与 `wenyan` 共享进度在刷新、离线和恢复后保持一致 |
| AC-P0-A11 | 报告一致性 | 24h/7d 保持率、自评分布、拼写错误分类和热力图可由同一状态事实解释 |
| AC-P0-A12 | 日志与隐私 | 恢复诊断不记录敏感正文或可识别个人信息；错误信息足以定位问题 |
| AC-P0-A13 | 部署差异 | 无 `/api/state` 的环境仍能完成学习、保存和恢复本地状态 |

### 5.4 P0 内容验收

### 5.9 发布门禁

一个版本进入 P0 发布候选时，至少要满足：

1. 6 本词书计数与 10,799 总盘一致。
2. `gaokao` 8 个乱序组、`curated` 6 个主题、`wenyan` 33 个单元均有完整性结果。
3. `curated` 与 `wenyan` 的共享进度映射通过验证。
4. 对本版本新增/修改的 fallback-example 有复核结论；存量 508 个唯一待审核词有公开分批计划，内容质量里程碑另要求全量结论。
5. 本版本影响范围内没有未解决的 C0 缺陷；C1 缺陷已修复或有正式豁免。
6. 至少一个确认成功的耐久层可用时，刷新、离线、指定单层存储失败、重复写入和 Schema 迁移测试通过；全部失败时不假报成功。
7. `/api/state` 不可用时，本地学习保存和恢复仍通过。
8. 390px 关键流程、文本放大和安全区验收通过。
9. 报告统计与底层学习事件一致。
10. 发布说明列出已验证范围、降级能力、未决风险和需要人工复核的内容。

进入 P1 阶段后，P0 的计数门禁、条件化状态耐久门禁、变更范围内 fallback 复核门禁和 390px 核心体验门禁必须持续保持，不得因新增学习功能而回退；WorkBuddy × Codex CLI / `ego-browser` 验证证据贯穿每次交付。

## 结论

拾词已经具备清晰的学习定位、覆盖高中至大学的 6 本词书矩阵、10,799 个词条以及从微循环到报告的完整产品闭环。当前最重要的演进不是盲目增加新的学习模式，而是把已有能力变成可信、可解释、可恢复和可维护的产品系统。

建议将资源优先投入两项 P0：第一，建立内容、学习状态和多层存储之间的稳定契约，在明确耐久层成功确认前提下保证恢复正确；第二，以 10,799 个书内词条为母体完成结构审计，对存量 508 个唯一 fallback 词分批复核、优先处理高风险 99 条，并把全量结论设为独立内容质量里程碑。WorkBuddy × 本机 Codex CLI 与 `ego-browser` 的需求—实现—独立验证协同从本轮 P0 开始贯穿；P1 继续增强学习体验与文言辨析，P2 在既有备份迁移上增加增量合并。商业化仅在授权、隐私与支付门禁满足后另行验证。
