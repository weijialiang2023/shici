# Codex 深度代码审计与协同架构演进提案

> 审计对象：`shici` 静态词书与间隔重复应用  
> 审计身份：协同架构师（Codex）  
> 依据范围：仅使用题目提供的已核实文件规模、模块名称与词书数量。本文不声称重新读取了源码；涉及内部实现的风险均明确标注为“结构风险”或“Phase 1 待核验项”。  
> 目标约束：零构建、静态部署、浏览器直接运行、保留离线 PWA 能力，并以 `shici.state.v1` 实现可验证、可恢复、非破坏式的数据迁移。

## 一、执行摘要

`shici` 当前已经具备完整产品闭环，但从代码体量看，已经进入明显的巨石应用阶段：

- 已核实总规模为 15,735 行，其中 CSS 9,649 行，占全部列明文件的约 61.3%。
- 业务 JavaScript 共 5,445 行；`app.js`、`store.js`、`ui.js` 合计 5,299 行，占 JavaScript 的约 97.3%。
- 6 本词书共 10,799 条内容，这是重构期间必须锁定的内容完整性基线。
- PWA、静态服务和内容数据已经具备分层条件，但当前文件边界尚不足以表达职责边界。

核心判断不是“文件太大，所以要拆”，而是：

1. 大文件使状态持久化、SRS 算法、DOM 副作用与路由控制难以独立验证。
2. 在线内容有 10,799 条，用户学习状态又持续增长，迁移与多标签页写入必须优先解决数据安全。
3. Service Worker 体量虽只有 95 行，但缓存版本错误可能直接造成“代码已更新、用户仍看到旧版本”的生产事故。
4. Python 内容处理与静态运行时需要形成明确的生产链路：源内容校验、确定性输出、清单签名、浏览器只读消费。

推荐策略为：

> 先冻结行为和数据，再建立状态安全层；随后拆分领域、存储、UI 与 App 控制层；最后进行内容管线、PWA、CSS、性能和可访问性产品化。

## 二、现有架构全貌与巨石模块技术债诊断

### 2.1 已核实规模基线

| 文件或资产 | 已核实规模 | 当前结构定位 | 主要风险 |
|---|---:|---|---|
| `index.html` | 301 行 | 单页入口、静态壳层 | 页面壳层可能同时承载结构、数据初始化与装配职责 |
| `js/app.js` | 2,264 行 | 应用总入口 | 路由、业务流程、TTS、事件协调可能集中在一个文件 |
| `js/store.js` | 1,657 行 | 状态与持久化 | 状态模型、SRS 调度、存储迁移和快照职责可能耦合 |
| `js/ui.js` | 1,378 行 | 页面渲染与交互 | DOM 查询、事件绑定、视图状态和业务判断可能混杂 |
| `js/data.js` | 146 行 | 词书数据装配 | 数据装配规则、数据版本和内容校验边界不清晰 |
| `css/styles.css` | 9,649 行 | 全站样式 | 选择器冲突、重复规则、级联依赖和响应式维护成本高 |
| `serve.py` | 245 行 | 本机静态服务 | 静态服务、开发便利逻辑和内容处理逻辑边界可能模糊 |
| `sw.js` | 95 行 | PWA 缓存与离线 | 缓存版本、更新策略和资源清单一致性风险高 |
| 6 本词书 | 10,799 条词条 | 只读内容资产 | 重复、缺失、编码、稳定 ID、内容版本和清单一致性风险 |

以下结构级比例值得作为后续治理指标：

- 核心 JavaScript 中 97.3% 集中在 `app.js`、`store.js`、`ui.js`。
- CSS 是当前单一文件规模最大的资产。
- 内容有 10,799 条，而 `data.js` 仅 146 行，说明内容主体与运行时装配之间需要明确的不可变数据边界。
- `sw.js` 只有 95 行，但它是高影响模块，不能以行数判断风险。

### 2.2 当前逻辑架构

根据现有文件划分，可抽象为以下运行结构：

```text
index.html
   │
   ├── js/app.js          应用装配、路由、流程、TTS 等控制逻辑
   ├── js/store.js        状态、持久化、SRS 调度、快照/迁移
   ├── js/ui.js           DOM 渲染、事件处理、页面反馈
   ├── js/data.js         词书装配与数据入口
   └── css/styles.css     全局视觉与响应式规则

sw.js                     离线缓存与应用壳更新
serve.py                  本机静态服务
6 本词书 / 10,799 条      只读内容资产
```

这个结构的优点是小项目起步快、部署简单、无需构建工具；问题是当功能增长到数千行时，职责只能靠开发者的记忆维持，无法通过模块依赖关系约束修改边界。

### 2.3 巨石模块诊断

以下“结构性表现”已由文件规模确认；“内部耦合判断”属于需要 Phase 1 行为冻结和依赖映射进一步验证的风险假设。

| 模块 | 严重度 | 诊断 | 预期债务表现 | 治理方向 |
|---|---|---|---|---|
| `js/app.js` | 高 | 应用入口过大 | 路由、复习流程、TTS、弹窗、统计和副作用容易相互调用 | 拆为 App 组合根、路由、复习控制器、TTS 控制器和错误边界 |
| `js/store.js` | 高 | 状态、算法与存储容易同居一处 | SRS 函数依赖 DOM、时间或 `localStorage`，导致不可测试；迁移代码可能直接改写旧状态 | 拆为纯 SRS 领域层、State Store 门面、持久化适配器、快照与迁移器 |
| `js/ui.js` | 中高 | 全部视图集中 | 每次渲染重新绑定事件、销毁不完整、业务条件散落视图、局部更新困难 | 按页面与组件拆分，统一视图模型、事件意图和挂载/销毁生命周期 |
| `css/styles.css` | 高 | 单文件 9,649 行 | 选择器重复、优先级竞争、颜色和间距散落、响应式覆盖链难追踪 | 建立 design tokens 与分层 CSS，先机械拆分，再逐步消除重复和无主规则 |
| `js/data.js` | 中 | 数据装配边界不清 | 内容与运行时代码耦合，词书结构变化时影响 UI 与 Store | 改为清单驱动加载，Python ETL 输出不可变结构化数据 |
| `serve.py` | 中 | 本机服务承担边界不明 | MIME、缓存、路径穿越、开发与生产行为不一致 | 明确为纯静态服务层，默认仅回环地址，补齐安全头和 MIME 测试 |
| `sw.js` | 高 | 缓存生命周期风险 | 更新未激活、旧缓存残留、代码与词书版本错配、离线白屏 | 以内容清单哈希生成缓存版本，等待激活与显式刷新，支持回退 |
| 6 本词书 | 高 | 10,799 条内容缺少明确质量门禁的风险 | 重复 ID、空字段、编码异常、跨版本词条漂移 | Python ETL、清单哈希、内容审计和人工发布批准 |

### 2.4 横切技术债

#### 状态安全债

10,799 条词条意味着学习进度可能覆盖大量实体。持久化层必须区分：

- 只读词书内容；
- 可变的用户学习状态；
- 轻量设置；
- 历史快照和恢复材料。

若用户状态与内容直接混存，任何词书升级、重排或删除都可能破坏进度关联。目标设计必须使用稳定词条 ID，不以数组下标作为进度键。

#### 领域算法债

SRS 算法应当是纯函数：给定卡片、评分和时间，只返回新卡片与复习事件。它不应读取 DOM、随机数、系统时钟、`localStorage` 或全局应用状态。否则同一输入无法复现，也无法对迁移前后的调度行为做差分验证。

#### UI 副作用债

UI 层应消费视图模型并发出意图，例如 `RATE_CARD`、`OPEN_BOOK`、`SPEAK_CURRENT_WORD`。UI 不应直接写持久化层，也不应自行决定 SRS 结果。这样可以避免“按钮点击一次、状态写两次、界面却显示第三种结果”。

#### PWA 发布债

静态应用没有版本化文件名时，尤其容易发生：

- `index.html` 已更新，但旧 JavaScript 仍被缓存；
- 词书数据进入新缓存，应用逻辑仍为旧版本；
- 新 Service Worker 安装失败后旧缓存未回退；
- 用户点击刷新后仍加载旧页面。

PWA 必须与应用版本、词书清单版本和缓存集合使用同一个发布标识。

#### 导入与内容安全债

如果支持用户导入状态或词书，必须进行：

- 文件大小限制；
- 结构校验；
- 未知字段保留；
- 文本转义；
- 禁止 `eval` 和动态脚本执行；
- 导入前快照；
- 导入失败时不替换当前状态。

#### 多标签页与会话一致性债

两个标签页同时写学习进度时，最后写入者覆盖会造成静默丢失。目标 Store 必须使用单调递增 `revision`、事务提交和冲突检测；发生冲突时保留双方快照，而不是自动覆盖。

#### 可测试性债

当前结构允许功能可用，却不利于证明功能可按预期运行。重构必须建立：

- SRS 纯函数测试向量；
- 状态迁移与导出回放测试；
- 词书清单和 10,799 条基线审计；
- ego-browser 端到端测试；
- Service Worker 更新与离线测试。

### 2.5 优先治理顺序

1. **用户状态不可丢**：快照、迁移、导入导出与多标签页冲突。
2. **SRS 行为不可漂移**：先冻结当前行为，再纯函数化。
3. **内容不可缺失**：锁定 6 本词书和 10,799 条基线。
4. **PWA 不可错版本**：缓存集合与清单哈希绑定。
5. **UI 与 CSS 可维护性**：拆组件、拆样式、降低级联冲突。
6. **性能与可访问性**：处理 10,799 条数据下的列表渲染、键盘操作和屏幕阅读器语义。

## 三、零构建静态兼容的目标分层架构

### 3.1 架构原则

1. **零构建**：不使用打包器、转译器或运行时构建步骤；直接部署 HTML、CSS、JavaScript、JSON 和 Python 脚本。
2. **原生 ES Modules**：通过浏览器原生模块划分边界，不使用框架依赖。
3. **单向依赖**：UI 不反向调用 App，Store 不依赖 UI，SRS 不依赖任何应用层。
4. **内容只读**：词书由 ETL 生成；运行时不得修改内容文件。
5. **状态集中写入**：只有 Store 层可以持久化用户状态。
6. **副作用收敛**：时间、存储、DOM、TTS、网络和 Service Worker 都可替换、可观测。
7. **渐进兼容**：Phase 1 保留旧入口适配器，所有拆分先以行为不变为目标。
8. **机器验证优先**：每个阶段都有可自动执行的数据、状态和 E2E 门禁。

### 3.5 核心数据流

#### 冷启动

```text
index.html
  → bootstrap.js
  → catalog-loader 读取 manifest.json
  → 按 manifest 加载词书
  → state-store 加载 shici.state.v1
  → 必要时执行受保护迁移
  → App 构造视图模型
  → UI 渲染
```

#### 复习评分

```text
用户点击评分
  → UI 发出 RATE_CARD 意图
  → App 调用 srs.schedule(card, rating, now)
  → Store 以 expectedRevision 提交新状态
  → 快照层记录恢复点
  → UI 接收新视图模型
```

#### TTS

```text
UI 发出 SPEAK 或 CANCEL_TTS
  → App 校验当前路由与卡片
  → TTS 控制器生成 speech token
  → 仅接受当前 token 的回调
  → 路由变化或快速连点时取消旧语音
```

#### 内容发布

```text
源词书
  → Python ETL
  → 结构校验与内容审计
  → 稳定 ID 分配
  → data/books/*.json
  → manifest.json 汇总哈希和数量
  → WorkBuddy 内容负责人批准
  → PWA 缓存版本更新
```

### 3.6 各层详细设计

#### Store 持久化与快照层

Store 是唯一的用户状态写入入口。建议公开接口保持小而稳定：

```js
stateStore.load();
stateStore.getSnapshot();
stateStore.commit(action, { expectedRevision });
stateStore.subscribe(listener);
stateStore.exportState();
stateStore.importState(file);
stateStore.getRecoveryStatus();
```

约束：

- 所有写操作携带 `expectedRevision`。
- 提交失败时，旧状态保持有效。
- UI 不感知 IndexedDB、`localStorage` 或具体迁移细节。
- 导入文件先校验，再写入新快照，不直接覆盖当前状态。
- 未知字段默认保留，避免未来版本降级时丢失扩展数据。

#### SRS 间隔重复算法层

目标接口示例：

```js
schedule(card, rating, now) → {
  card: nextCard,
  event: reviewEvent
}

getDueCards(cards, now) → card[]
```

Phase 1 不允许顺便修改算法。必须先用当前实现生成测试向量，再抽取为纯函数。若产品需要新算法，应新增明确的 `algorithmVersion` 并独立迁移，不与文件拆分混在同一次发布中。

#### UI 渲染层

建议页面组件包括：

- 应用壳与导航；
- 词书列表；
- 当前复习卡片；
- 统计页；
- 设置与导入导出；
- 恢复模式与冲突提示；
- 通用弹窗、提示和空状态。

关键规则：

- 每个组件有明确 `mount/destroy`。
- 事件使用根节点委托，避免每次渲染反复绑定 window 或 document。
- 10,799 条内容不得一次性全部进入 DOM；列表采用分页、窗口化或按需加载。
- UI 只接受视图模型，不自行推导 SRS 结果。
- 文本内容渲染必须默认转义，禁止把词书字段直接作为未验证 HTML。
- 恢复模式和“尚未保存”状态必须是显式 UI 状态，不能静默吞掉错误。

#### App 路由与 TTS 控制层

建议使用无依赖 Hash 路由，例如：

```text
#/library
#/review/<bookId>
#/stats
#/settings
#/recovery
```

App 层负责：

- 依赖组装；
- 路由与页面生命周期；
- 复习用例；
- 导入导出协调；
- 迁移与恢复模式；
- TTS 状态机。

TTS 至少应区分：

```text
idle → speaking → cancelling → idle
              ↘ error
```

快速切换卡片、离开路由或重复点击时，通过递增 `speechToken` 使旧回调失效，避免上一张卡片的朗读结果覆盖当前界面。

#### CSS 分层

当前 9,649 行应做“先搬家、后治理”：

1. 建立颜色、间距、字号、圆角、阴影和断点 tokens。
2. 按 reset、base、layout、component、page、responsive 拆分。
3. 使用多个明确 `<link>` 顺序加载，避免 `@import` 造成串行请求瀑布。
4. 先只做规则归位，不在同一次提交中大规模改视觉。
5. 第二阶段再删除重复规则、降低 `!important`、合并相近断点。
6. 组件样式遵循单一命名域，禁止跨页面以元素选择器互相污染。

建议把“非生成 JavaScript 文件不超过约 500 行、CSS 模块不超过约 500 行”作为 review 警戒线，而非绝对教条。超过时必须说明职责为什么不能继续拆分。

#### Python ETL 与内容审计层

ETL 必须确定性输出：

- 相同输入产生相同排序、相同 ID、相同 JSON 语义；
- 每本词书记录独立 SHA-256；
- `manifest.json` 记录每本数量、总数量、输出格式版本和内容哈希；
- 当前发布基线锁定为 6 本、10,799 条；
- 任何数量变化必须经过显式内容审计和 WorkBuddy 内容负责人批准。

建议的审计规则：

| 检查 | 级别 | 处理 |
|---|---|---|
| JSON 结构不符合 schema | 阻断 | 停止发布 |
| 词条 ID 重复 | 阻断 | 定位来源并修正映射 |
| 词条总数为 10,799 之外的未批准变化 | 阻断 | 必须显式批准 |
| 书名、词条、释义空值 | 阻断或按字段定义处理 | 形成逐条报告 |
| 非法 Unicode、控制字符、异常空白 | 阻断或修复建议 | 不静默清洗 |
| 同一 ID 对应内容变化 | 警告并审阅 | 判断正常修订还是 ID 错误 |
| 数组下标式 ID | 阻断 | 改为稳定内容 ID |
| manifest 哈希不匹配 | 阻断 | 禁止发布缓存清单 |
| 重复标题但内容不同 | 警告 | 人工确认是否应合并 |

`audit_content.py` 应既支持发布前检查，也能在 CI 或 WorkBuddy 的审核任务中生成机器可读报告。审计失败不得生成可通过发布门禁的清单。

#### PWA 与本机服务层

`sw.js` 应只负责资源缓存，不包含业务逻辑：

- Service Worker 版本由应用版本和 `manifest.json` 内容哈希共同决定；
- 预缓存集合必须一次性完成，失败不得激活半套资源；
- 新版本进入 `waiting` 时向用户显示“更新后可刷新”；
- 不在无提示情况下替换正在使用的资源；
- 激活后仅清理本应用旧缓存；
- 离线导航有明确 fallback；
- `index.html`、入口模块和 `manifest.json` 采用一致发布版本。

`serve.py` 保持纯静态服务：

- 默认绑定 `127.0.0.1`，不默认暴露公网；
- 严格规范化路径，防止目录穿越；
- 为 `.js`、`.json`、`.webmanifest`、`.wasm` 等配置正确 MIME；
- 对 `sw.js` 和入口 HTML 设置适合更新的缓存策略；
- 仅提供静态文件，不承担 SRS、状态或词书编辑职责。

- Store、迁移、SRS：高见远 + Codex；

- 数据数量与哈希一致；

- 关键 E2E 通过；
- 离线与更新策略通过；

#### 第六步：发布与留痕

- 应用版本；
- 词书 manifest 哈希；
- `shici.state.v1` schema 版本；

- 内容审计报告；

### 4.4 Codex 的自动化职责

#### CLI 非交互执行

Codex 任务应具备可重复输入和结构化输出，适合以下场景：

- 批量静态扫描；
- 模块依赖图生成；
- 重复 CSS 规则报告；
- 状态 schema 比对；
- 测试失败定位；
- 代码 Review；
- 重构补丁生成。

#### Python ETL 与内容审计

Codex 维护内容流水线，但不拥有内容编辑权。它可以：

- 识别重复和缺失；
- 计算哈希；
- 生成稳定清单；
- 比较版本差异；
- 输出候选修复建议；
- 阻止错误数据进入发布清单。

#### ego-browser 自动化 E2E

建议覆盖：

| 场景 | 验证点 |
|---|---|
| 冷启动 | 6 本词书可加载，manifest 数量为 10,799 |
| 选择词书 | 正确进入复习流程，URL 与视图一致 |
| 提交评分 | SRS 结果写入，刷新后仍存在 |
| 多次重载 | 状态 revision 单调增长且无重复写入 |
| 快速切换卡片 | 不出现旧卡片覆盖新卡片 |
| TTS 连点与路由离开 | 旧语音回调失效，无错误状态悬挂 |
| 导入错误文件 | 当前状态不被覆盖，出现可恢复提示 |
| 迁移旧状态 | 所有已知字段、未知扩展字段和进度均保留 |
| 模拟主快照损坏 | 自动回退上一快照并进入告警状态 |
| 两个标签页并发提交 | 检测冲突，不执行静默最后写入覆盖 |
| 离线重载 | 应用壳和词书可打开 |
| 新 Service Worker 等待 | 用户收到更新提示，旧页面不混合新旧资源 |
| 键盘与焦点 | 关键复习操作无需鼠标完成 |
| 小屏幕 | 导航、卡片和弹窗不遮挡关键操作 |

Codex 的 E2E 输出应包含步骤、断言、截图、控制台错误和网络/缓存状态摘要。截图只作为人工复核材料，断言不能只看页面是否“看起来正常”。

## 五、Phase 1–3 重构路线图

### 5.1 总体路线

| 阶段 | 主题 | 核心目标 | 不做什么 | 退出条件 |
|---|---|---|---|---|
| Phase 1 | 行为冻结与零丢失底座 | 锁定数据、行为与状态，建立快照和测试 | 不改 SRS 结果，不进行视觉重设计，不删除旧状态 | 内容基线、行为基线、恢复演练全部通过 |
| Phase 2 | 模块解耦 | 拆 Store、SRS、UI、App、TTS 与 CSS | 不顺手改交互，不新增业务功能 | 依赖单向、核心文件显著缩小、回归通过 |
| Phase 3 | 产品化与发布硬化 | 内容管线、PWA、性能、可访问性和兼容退役 | 不在不稳定基础上增加大功能 | 离线、更新、数据审计、性能与无障碍均过关 |

建议以迭代而非承诺具体日历周数推进；如果团队按双周迭代，可将 Phase 1 估算为约 1–2 个迭代，Phase 2 约 2–3 个迭代，Phase 3 约 2–4 个迭代，最终以门禁通过为准。

### 5.2 Phase 1：行为冻结与零丢失底座

#### 目标

先证明“现在的行为是什么”和“用户数据如何不丢”，再进行模块迁移。

#### 工作项

1. 建立当前存储键、状态字段、导入导出格式和 SRS 行为清单。
2. 生成词书 manifest：
   - 6 本；
   - 总数 10,799；
   - 每本数量、SHA-256、schema 版本、生成时间。
3. 建立 SRS golden fixtures，覆盖评分、到期、重复复习和边界时间。
4. 在现有存储入口外加 Store 门面，但初期不改变旧写入结果。
5. 引入快照层，在每次正式迁移和导入前保存原始状态。
6. 实现 `shici.state.v1` 首版 envelope 和迁移器。
7. 建立 ego-browser 主流程、重载和恢复场景。
8. 建立静态检查：UI 不得直接访问持久化；SRS 不得调用 DOM 或存储。

#### Phase 1 的迁移策略

建议采用“观察—影子副本—切换”的顺序：

```text
旧状态原样保留
  → 读取并记录 schema
  → 生成只读 v1 影子快照
  → 校验字段和语义
  → 回放复习状态
  → 才允许 v1 成为写主路径
```

不允许在首次读取旧状态时立即删除或覆盖旧键。

#### 退出条件

- 6 本词书和 10,799 条基线可重复审计。
- 当前 SRS 行为有完整测试向量。
- 旧状态成功迁移到 v1，字段无丢失。
- 迁移失败时旧状态仍可读。
- 导入导出往返语义一致。
- 主快照损坏可以恢复。
- 重载、刷新、离线和再次联网后的状态一致。
- 严过关完成恢复演练，高见远完成架构 Review。

### 5.3 Phase 2：模块解耦

#### 目标

把“文件行数”转换为“可验证的职责边界”，同时保持用户可见行为不变。

#### 工作项

1. 新建 `js/domain/srs.js`：
   - 纯函数；
   - 显式传入时间；
   - 不依赖 Store、DOM 或 TTS。
2. 新建 `js/store/state-store.js`：
   - 页面和 UI 不再直接调用底层存储；
   - 提供 revision 提交与订阅；
   - 统一导入导出、迁移和恢复。
3. 拆分 `js/ui.js`：
   - shell、词书列表、复习卡片、统计、设置、恢复提示；
   - 每个组件拥有挂载与销毁生命周期。
4. 拆分 `js/app.js`：
   - bootstrap；
   - router；
   - review-controller；
   - tts-controller；
   - error-boundary。
5. 在 Phase 2 中期将 `js/app.js` 降级为兼容入口，只负责装配和旧接口转发。
6. 按层拆分 CSS，但先保持计算后的视觉结果不变。
7. 处理 10,799 条内容下的列表渲染：分页或窗口化，禁止全量 DOM 节点。
8. 将多标签页写冲突纳入 E2E。

#### 结构目标

- `app.js` 不再是主要业务实现文件；
- `store.js` 不再承担 UI 展示；
- `ui.js` 不再直接调用持久化；
- `srs.js` 可在无浏览器 DOM 的环境下验证；
- 非生成 JS 文件超过约 500 行需要 Review 例外说明；
- 不允许循环依赖。

#### 退出条件

- 同一评分输入产生与 Phase 1 fixtures 相同的结果。
- 旧存储读取兼容，v1 写入稳定。
- 多标签页冲突不会静默覆盖。
- 页面路由、复习、统计、设置、导入导出全部回归通过。
- CSS 拆层前后视觉截图差异只允许预先说明的微小变化。
- 核心 E2E 与恢复场景全绿。

### 5.4 Phase 3：内容管线、PWA 与产品硬化

#### 目标

## 六、`shici.state.v1` 零丢失防护机制

### 6.1 防护边界

这里的“零丢失”指：

> 在应用可控的保存、升级、迁移、导入、冲突和浏览器事务异常路径中，不静默覆盖、不主动删除、不产生不可恢复的单点状态；任何失败都必须保留上一份有效快照并给出恢复路径。

它不等于以下情况下的绝对恢复：

- 用户主动清除站点数据；
- 浏览器存储被系统回收；
- 设备损坏；
- 用户拒绝提供导入文件且所有本地副本均消失。

因此还应提供显式用户导出，并尝试申请持久化存储许可。

### 6.2 逻辑结构

```json
{
  "schemaVersion": "shici.state.v1",
  "revision": 128,
  "parentRevision": 127,
  "savedAt": "2026-11-22T00:13:30+08:00",
  "appVersion": "release-id",
  "catalogVersion": "sha256:catalog-manifest",
  "payloadSha256": "sha256:canonical-data",
  "migration": {
    "id": "migration-id",
    "from": "legacy",
    "warnings": []
  },
  "data": {
    "...": "保留现有已知状态字段原名和语义"
  },
  "extensions": {
    "legacyUnknownFields": {}
  }
}
```

设计要点：

- `schemaVersion` 固定为 `shici.state.v1`。
- `revision` 单调递增。
- `parentRevision` 指向上一提交，便于审计。
- `catalogVersion` 记录本次状态对应的词书清单，不用于直接把旧进度判为无效。
- `data` 不得包含 10,799 条只读词书全文；词书是独立只读内容。
- 未识别字段进入 `extensions.legacyUnknownFields` 原样保留。
- 校验和只覆盖确定性的 `data` 规范序列化，不覆盖包含校验和自身的整个对象，避免循环依赖。

### 6.3 推荐存储模型

建议使用 IndexedDB 作为 v1 主存储，避免大对象、快照和配额下的单键写入风险：

```text
数据库：shici
├── state      当前有效 envelope
├── snapshots  不可变历史快照
└── meta       迁移记录、最后 revision、恢复标记
```

`localStorage` 中现有旧状态键在迁移后至少保留两个稳定版本，且迁移过程不得修改其原始字符串。

如果目标环境必须继续使用 `localStorage`，则采用双槽方案：

```text
shici.state.v1.slot.a
shici.state.v1.slot.b
shici.state.v1.pointer
```

但 IndexedDB 事务更适合多个存储对象一次提交，也更能承载快照与较大的用户状态，因此作为首选方案。

### 6.4 提交事务

每次用户状态提交执行：

1. 在内存中生成候选状态。
2. 校验 schema。
3. 计算规范化 SHA-256。
4. 在同一个 IndexedDB 读写事务中：
   - 读取当前 revision；
   - 校验 `expectedRevision`；
   - 写入新 envelope；
   - 写入不可变快照；
   - 更新 meta。
5. 事务成功后广播新 revision。
6. UI 只有在事务完成后才显示“已保存”。

如果事务失败，旧状态保持不变。不得采用以下危险模式：

```text
先删除旧状态 → 再写入新状态
```

或：

```text
写入失败后仍显示保存成功
```

### 6.5 多标签页一致性

- 每次提交携带 `expectedRevision`。
- 若 revision 不匹配，事务中止，不覆盖其他标签页结果。
- 通过 `BroadcastChannel` 通知其他标签页刷新视图。
- 页面不可见时再次恢复，先重新读取最新 revision。
- 冲突时：
  - 保存“冲突前本地快照”；
  - 保存“其他标签页当前快照”；
  - 显示恢复或导出提示；
  - 不自动执行最后写入者覆盖。
- 支持 Web Locks 时，将写入串行化作为额外保护，但 IndexedDB 的 revision 校验仍是最终事实来源。

### 6.6 迁移流程

旧状态迁移必须满足：

```text
读取旧状态原始字符串
  → 保存原始快照
  → 解析
  → 生成候选 v1
  → schema 校验
  → 语义比较
  → 写入 IndexedDB
  → 读回并再次校验
  → 更新迁移标记
  → 多一次重载验证
```

具体规则：

1. 迁移开始前保存 `pre-migration-raw` 快照。
2. 旧状态字段按原语义进入 `data`。
3. 未识别字段不丢弃，进入 `extensions`。
4. 不把数组下标当作长期稳定 ID。
5. 词书升级导致找不到对应内容的进度不得删除，先作为“保留进度”保存。
6. 任一校验失败时：
   - 不写入正式 v1；
   - 进入恢复模式；
   - 允许下载原始旧状态；
   - 提供重新读取或恢复上一快照入口。
7. 旧状态键在至少两个稳定版本内不删除。
8. 旧应用回滚不能直接读取 v1 时，必须通过导出与降级转换流程处理，禁止声称“换回旧代码即自动兼容”。

### 6.7 自动与手动快照

建议保留：

- 每次成功提交的轻量快照；
- 每次迁移前的原始快照；
- 每次导入前的当前状态快照；
- 每个应用版本首次成功启动后的稳定快照；
- 用户主动导出的完整 JSON。

快照保留策略可以是“最近 N 份 + 每个版本首份”，避免无限增长。具体 N 需按实际状态大小和存储额度测量，建议先在目标设备上完成容量基线。

### 6.8 恢复顺序

应用启动时按以下顺序选状态：

```text
1. v1 当前 envelope，校验 schema + revision + 哈希
2. 最新有效 v1 快照
3. 旧状态原始键，只读恢复
4. 用户导入文件
5. 恢复模式，不允许静默创建空状态覆盖
```

只有确认用户没有旧状态且主动选择“新建”时，才允许创建全新的空 v1。启动失败不能直接清空状态并继续。

### 6.9 导入、导出与配额

#### 导出

- 输出完整 envelope；
- 包含 schema、revision、catalogVersion、校验和；
- 文件名包含版本和时间；
- 导出前验证当前内存状态可序列化。

#### 导入

- 限制文件大小；
- 先解析到临时对象；
- 校验 schema；
- 保存当前状态为 `pre-import` 快照；
- 写入不破坏当前状态的候选事务；
- 成功后显示 revision 和恢复入口；
- 失败时保持原状态。

#### 配额不足

- 捕获存储错误；
- 不清除旧快照以“腾空间”；
- 标记当前状态为“尚未持久化”；
- 阻止误导性成功提示；
- 提示用户导出，并允许清理明确指定的低价值旧快照。

### 6.10 `shici.state.v1` 验收矩阵

| 测试 | 预期结果 |
|---|---|
| 读取旧状态 | 所有已知字段和未知字段保留 |
| 迁移后再重载 | revision、内容、调度状态一致 |
| 写入事务失败 | 当前有效状态不变化 |
| 最新快照损坏 | 自动回退上一份有效快照 |
| 指针/当前记录损坏 | 进入可解释的恢复模式 |
| 两个标签页并发提交 | revision 冲突被检测，不静默覆盖 |
| 导入非法 JSON | 当前状态不变 |
| 导入合法 v1 | 导入前快照存在，导入后可导出回放 |
| 词书版本变化 | 进度按稳定 ID 保留，未知条目不被清除 |
| 浏览器存储额度不足 | 明确告警、允许导出、不删除旧数据 |
| 页面关闭前写入中 | 事务要么完整提交，要么完全回滚 |
| 旧版本发布回退 | 通过降级转换流程恢复，不假设直接兼容 |

## 七、发布门禁与最终成功标准

### 7.1 数据门禁

- 6 本词书存在。
- 总数为 10,799，除非有明确批准的内容变更单。
- 每本词书和 manifest 哈希一致。
- 重复 ID 为零。
- 非批准 schema 漂移为零。
- 内容审计报告归档。

### 7.2 状态门禁

- 旧状态迁移成功。
- 迁移不丢未知字段。
- 导入导出语义回放一致。
- 主快照损坏可恢复。
- 多标签页冲突不覆盖。
- 配额异常可见、可导出、可恢复。

### 7.3 行为门禁

- SRS fixtures 与冻结基线一致。
- 快速切换卡片不串状态。
- TTS 过期回调不污染当前卡片。
- 路由刷新后恢复正常。
- 10,799 条内容列表不导致全量 DOM 渲染。

### 7.4 PWA 门禁

- 离线冷启动可用。
- 新版本资源不混入旧 HTML。
- 缓存安装失败不会激活半套资源。
- 更新提示明确。
- 回滚缓存和回滚应用版本有演练记录。

### 7.5 Review 门禁

- 无循环依赖。
- UI 不直接写持久化。
- SRS 不读取 DOM、时间全局或存储。
- Store 不依赖 UI。
- Service Worker 不承载业务。
- Python ETL 是词书发布的唯一入口。
- 超过模块体积警戒线的文件有明确理由或后续拆分任务。

## 八、最终架构结论

`shici` 目前的核心问题不是缺少功能，而是功能增长已经超过了单文件模块边界的承载能力。最危险的并不是 9,649 行 CSS，而是 `app.js`、`store.js` 与用户状态安全之间的关系：只要状态模型、SRS 调度、迁移和持久化没有明确边界，任何一次看似局部的重构都可能改变用户学习进度。

因此建议采用以下决策顺序：

1. **先把 6 本词书、10,799 条内容和当前复习行为冻结成机器可验证基线。**
2. **先建立 `shici.state.v1`、快照、冲突检测和恢复机制，再切换写路径。**
3. **将 SRS 抽为纯函数，将 Store 抽为唯一持久化门面。**
4. **拆分 UI、App 路由和 TTS，让页面层只消费视图模型、只发出意图。**
5. **用 Python ETL 和审计约束内容，用 ego-browser 与 Codex 自动化证明用户流程。**
6. **最后处理 Service Worker、CSS、性能、可访问性和旧格式退役。**

这条路线保留了零构建和静态部署的核心优势，同时把系统从“多个大文件组成的可用应用”演进为“可证明数据不丢、依赖单向、内容可审计、发布可回滚的静态 PWA”。协同上，WorkBuddy 团队掌握产品与内容判断，Codex 负责自动化审计、ETL、重构、E2E 和 Review 证据，双方通过契约、任务卡和发布门禁闭环，而不是依赖口头约定维持架构边界。
